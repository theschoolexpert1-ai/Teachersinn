# TeachersInn Supabase migration plan

## Current state and Stage A boundary

TeachersInn currently runs as one Node.js process. `backend/src/server.js` owns routing and business rules, `backend/src/db.js` opens the SQLite database synchronously, and `backend/src/security.js` implements scrypt passwords, server-side sessions, CSRF, validation, and rate limiting. The browser calls the same-origin `/api` routes and does not hold authentication tokens.

Stage A adds a dormant Supabase foundation. `DATA_BACKEND` continues to default to `sqlite`; selecting `supabase` intentionally fails until the data adapter and Auth integration are complete. No migration in this directory is automatically executed by the application.

## Target architecture

```text
Vanilla browser application
        |
        | same-origin API + server-managed Supabase Auth session
        v
Existing Node.js HTTP server
        |-- user-scoped Supabase client (publishable key + verified user token)
        |-- tightly scoped admin client (server secret only)
        v
Supabase Auth + PostgreSQL/RLS + Storage
```

The preferred authentication design preserves HTTP-only browser cookies. The Node server exchanges credentials with Supabase Auth, stores refresh/access material only in encrypted or signed HTTP-only Secure cookies, refreshes sessions server-side, and validates identities with `auth.getUser()` before deriving the application user UUID. No endpoint may accept a frontend-supplied user ID as identity.

The Supabase secret key bypasses RLS. It must remain server-only and should be used only for audited identity migration, administrative Auth operations, and operations that cannot safely run with a user-scoped client.

## Schema mapping

The migrations preserve every domain represented by SQLite:

| SQLite source | PostgreSQL target | Identity treatment |
|---|---|---|
| `users` | `auth.users`, `profiles`, `account_settings` | Auth UUID is canonical; `profiles.legacy_id` retains traceability |
| `sessions` | Supabase Auth sessions | Existing custom tokens are not migrated |
| `audit_log` | `audit_log` | UUID user reference plus optional legacy ID |
| Learning tables | Same logical table names | User foreign keys become UUID |
| Workshop tables | Same logical table names | Attendance remains explicit and defaults false |
| Connections/messages | Same logical table names | Both participants become Auth UUIDs |
| Communities/posts/replies | Same logical table names | Author references become Auth UUIDs |
| Tickets/replies | Same logical table names | Owner/author references become Auth UUIDs |
| Mentorships | `mentorships` | Mentor and mentee become Auth UUIDs |
| Tutorials/views | Same logical table names | View owner becomes Auth UUID |
| Lesson plans | `lesson_plans` | Owner becomes Auth UUID |
| Jobs | `jobs` | Optional posting user becomes Auth UUID |
| Notifications | `notifications` | Recipient becomes Auth UUID |

Integer content IDs remain `bigint generated by default as identity`. Explicit legacy IDs can therefore be inserted during migration, after which each sequence must be advanced to the maximum imported ID.

`legacy_user_map` is the only authorized bridge between an old integer user ID and a new Auth UUID. Mapping by row order is forbidden.

## Password and account migration

The existing passwords are scrypt hashes. Supabase Auth stores bcrypt hashes, so the SQLite password hashes must not be copied into `auth.users.encrypted_password`.

Use a controlled claim process:

1. Normalize and deduplicate existing emails in a read-only preflight report.
2. Classify demo/system accounts separately; do not invite them automatically.
3. Create or invite each real user through the Supabase Admin API without setting a known password.
4. Record the returned UUID in `legacy_user_map` before importing related records.
5. Send a branded claim/password-setup link to the verified email address.
6. Mark the mapping `claimed` only after Supabase confirms the account and the user completes the flow.
7. Preserve suspended state in `account_settings`; block suspended accounts at the Node API and RLS-sensitive workflows.
8. Require administrators to claim accounts normally, then promote them in a separately audited operation.

Existing custom sessions are invalidated at cutover. Users must establish new Supabase sessions. Password hashes, plaintext passwords, generated shared passwords, and custom session tokens must never enter migration exports.

## Repeatable data migration sequence

All steps first run against an isolated development project, then staging. Production requires explicit authorization.

1. Create a consistent SQLite backup using SQLite's backup API while the application remains available.
2. Verify the backup with `PRAGMA integrity_check` and record its SHA-256 hash.
3. Generate a preflight manifest containing table counts, duplicate-email counts, orphan counts, ID ranges, and timestamp parsing failures. Do not include password hashes.
4. Apply the reviewed Supabase migrations to an empty target.
5. Create Auth identities through the Admin API and populate `legacy_user_map` idempotently by `legacy_user_id` and normalized email.
6. Import `profiles` and `account_settings` with upserts keyed by UUID.
7. Import non-user parent tables with explicit legacy IDs: courses, lessons, workshops, communities, tutorials, and jobs.
8. Import user-related and child tables by joining every integer user reference through `legacy_user_map`.
9. Import audit entries last; retain unmapped legacy IDs with a null UUID.
10. Advance identity sequences to the maximum imported ID.
11. Reconcile every source/target table count, all unmapped users, certificate-code uniqueness, and all foreign-key relationships.
12. Run API compatibility, RLS, Auth, and Storage tests against staging.

Each import batch must record a migration run ID, source backup hash, start/end time, row counts, rejected rows, and error details outside user-visible tables. Failed batches must be safe to repeat through stable primary keys and upserts.

## Storage design

- `profile-photos`: public delivery; only the owning user can create, replace, or delete objects under `<auth-uuid>/...`.
- `professional-documents`: private CV/resume documents; owner-only access; signed URLs should have short expirations.
- `course-resources`: private authenticated reads; administrator writes.
- `community-attachments`: authenticated reads; uploader-owned writes and deletes.

Bucket limits and MIME allowlists are defined in SQL. The Node upload layer must still validate magic bytes, extension, declared MIME type, size, and sanitized object names before calling Storage. Stage A adds no upload UI.

## Cutover runbook

1. Announce a maintenance window and stop new writes.
2. Close the Node process cleanly so SQLite WAL contents are checkpointed.
3. Create and verify the final SQLite backup; retain the original database, WAL, and SHM files unchanged.
4. Record the final preflight manifest and backup hash.
5. Apply migrations to the production Supabase project.
6. Create/verify Auth mappings and run the idempotent application-data import.
7. Reconcile counts, orphans, certificates, administrator roles, and sampled timestamps.
8. Run critical staging-style workflows against production with controlled accounts.
9. Configure server secrets and enable the Supabase backend only for the maintenance deployment.
10. Verify registration, claim/recovery, login/logout, profiles, learning, workshops, network, messages, communities, jobs, support, administration, Storage, and public certificate verification.
11. Reopen writes and monitor Auth failures, API errors, query latency, and Storage denials.

## Rollback

Before reopening writes, rollback means redeploying the SQLite build and restoring the verified pre-cutover database backup. If writes have reopened on Supabase, do not blindly switch back: first stop writes, export the delta, reconcile it against the SQLite backup, and obtain an explicit rollback decision. Keep the SQLite backup read-only until the retention policy is approved after a stable production period.

## Required project configuration before Stage B

- Separate development, staging, and production Supabase projects.
- Site URL and allowed redirects for each environment.
- Email confirmation and password recovery templates.
- Production SMTP configuration and delivery monitoring.
- `SUPABASE_URL`, publishable key, and server secret injected by the deployment secret manager.
- A direct database connection for migrations and a suitable pooled connection only where the future adapter needs it.
- Key rotation, access logging, backup/PITR, and administrator access policies.
- A decision on cookie encryption/signing and refresh-token rotation in the Node session bridge.

## Stage B exit criteria

Stage B may begin after the migrations execute successfully on a local or development Supabase stack and RLS tests pass with anonymous, teacher, mentor, administrator, and server-secret contexts. Stage B should implement the server-managed Auth bridge, registration confirmation, recovery, logout, refresh, suspended-user enforcement, and account claim flow while SQLite remains the application data source.

## Stage A.1 Supabase Cloud validation runbook

TeachersInn Stage A.1 uses a dedicated Supabase Cloud development project. Docker and the local Supabase stack are not part of this workflow. The integration suite is deliberately excluded from `npm test`; it creates and removes disposable Auth users and application rows and must never target production.

Create or select an empty disposable project whose name clearly identifies it as development. Record its 20-character project reference from the Dashboard URL. Generate a personal access token for the CLI, and obtain the project's publishable and secret keys from the API Keys settings. Supply all credentials in the current shell or a secret manager; never commit them or paste them into documentation.

Authenticate and verify the exact project before linking:

```powershell
$env:SUPABASE_ACCESS_TOKEN = '<personal access token>'
npx supabase projects list --output json
npx supabase link --project-ref '<development project reference>'
npx supabase migration list --remote
npx supabase db push --dry-run --remote
```

Stop if the selected project is not the intended disposable development project, if unexpected application tables or migration versions already exist, or if the dry run includes destructive statements. Do not use remote reset, migration repair, or direct Dashboard schema edits. After reviewing a safe dry run, deploy pending migrations and confirm history:

```powershell
npx supabase db push --remote
npx supabase migration list --remote
```

Configure the integration test in the same PowerShell session. The secret key bypasses RLS and is used only for disposable setup, administrator promotion, validation, and cleanup:

```powershell
$env:RUN_SUPABASE_INTEGRATION = '1'
$env:SUPABASE_TEST_ALLOW_REMOTE = '1'
$env:SUPABASE_TEST_ENVIRONMENT = 'development'
$env:SUPABASE_TEST_PROJECT_REF = '<development project reference>'
$env:SUPABASE_TEST_URL = 'https://<development project reference>.supabase.co'
$env:SUPABASE_TEST_PUBLISHABLE_KEY = '<development publishable key>'
$env:SUPABASE_TEST_SECRET_KEY = '<development secret key>'
npm run test:supabase
```

The suite refuses remote execution unless the environment is explicitly `development` and the project reference exactly matches the Supabase URL hostname. `SUPABASE_DB_URL` or the database password is needed only when the linked CLI workflow cannot establish its database connection; prefer the CLI link workflow and do not pass database passwords on a command line.

The suite validates anonymous denial, profile and account ownership, prevention of role escalation, administrator-only legacy mappings and audit data, enrollment and lesson-progress ownership, certificate RPC output, connection/message/ticket/mentorship isolation, and Storage ownership, read privacy, MIME, size, and administrator-write rules. It uses three teacher identities, one administrator identity, an anonymous client, and a server-secret client.

If the remote migration dry run or push fails, inspect the first failing migration and do not proceed to Stage B. A passing SQLite unit suite is not a substitute for PostgreSQL, RLS, Auth, and Storage execution.

### Stage A.1 execution status (2026-11-12)

Stage A.1 completed successfully against the dedicated `teachersinn-development` Supabase Cloud project (`ivnmrhwxdawmzaakdhec`). The authenticated project identity, health, database connection, empty pre-migration application schema, and dry-run contents were verified before deployment.

Migrations `202611120001`, `202611120002`, and `202611120003` are recorded remotely. The first attempt at migration 3 exposed a nonessential `COMMENT ON TABLE storage.objects` statement that the hosted migration role could not execute because Supabase owns that managed table. Migration 3 rolled back, the unapplied migration was corrected by removing only that comment, a second dry run showed only migration 3 pending, and it then applied successfully.

The cloud integration suite passed all six tests, including anonymous/Auth identities, cross-user RLS isolation, administrator authorization, certificate verification, and Storage ownership, privacy, MIME, size, deletion, and signed-URL behavior. The local regression suite passed all 18 tests and `npm audit --audit-level=high` reported zero vulnerabilities. Final cleanup left zero Auth users and zero rows in every application table; the four configured Storage buckets remain as the intended persistent infrastructure.

Stage A.1 therefore satisfies the database/security validation gate for planning Stage B. Stage B has not been started, SQLite remains the active backend, and beginning the authentication migration still requires a separate explicit task and implementation review.
